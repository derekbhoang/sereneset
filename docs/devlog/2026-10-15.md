## Decisions & why

- **Decision:** Include organization IDs in application relationships and tenant-scoped queries.
  - **Why:** Keep related records within the same workspace and enforce that boundary in both the database and services.
- **Decision:** Keep AI suggestions separate from tasks until an explicit, authorized apply action.
  - **Why:** Let users review, edit, and exclude suggestions before adding work to the project.
- **Decision:** Apply each plan in one transaction under a parent-plan lock.
  - **Why:** Prevent partial application and duplicate tasks from concurrent requests or retries.
- **Decision:** Retry failed generation by creating a new plan.
  - **Why:** Preserve the previous attempt and keep failed and applied plans terminal in the MVP.

## Learned

- Multi-tenant design separates global user identities from workspace membership and organization-owned data. In this model, `organization` is the tenant boundary, and every application row carries an `organization_id`.
- Tenant isolation uses several protection layers:
  - **Authentication and authorization:** Identify the user, resolve the active organization on the server, and verify current membership and permission for the action. Selecting a workspace does not grant access.
  - **Query scoping:** Include the authorized organization in reads, updates, deletes, joins, counts, and bulk operations, even when looking up a globally unique ID.
  - **Write validation:** Set ownership from the authorized server context, validate related IDs within that tenant, and keep organization ownership immutable.
  - **Database constraints:** Require organization ownership and use composite foreign keys such as `(organization_id, project_id)` to prevent relationships across tenants. These enforce data integrity; authorization checks still control access.
  - **Background jobs and caches:** Carry organization context into jobs and cache keys, and make workers recheck tenant relationships before writing results.
- A unique task reference on a suggestion does not make application idempotent by itself; the plan status, locking, and transaction need to work together.
- Clearing a nullable reference in a composite tenant foreign key must preserve the required organization ID.
- Queue redelivery alone cannot recover a crashed generation under the proposed lifecycle; timeout handling and a new plan request are needed.

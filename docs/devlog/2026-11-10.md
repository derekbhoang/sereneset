# Devlog — 2026-11-10

## Summary

Built the first application API for projects from the MVP data model, with workspace ownership, shared validation contracts, cursor pagination, and explicit action permissions. Verified the HTTP flow and database integrity rules, and aligned the listing query with its index.

## What I built / changed

- Added the `project` Drizzle schema and additive `0001_sweet_mordo` migration, including its snapshot and journal entry. Projects use generated UUIDs, a required name, nullable description, and timezone-aware timestamps with millisecond precision.
- Added organization and creator foreign keys with `ON DELETE CASCADE` and `ON DELETE RESTRICT`, respectively. Added `UNIQUE (organization_id, id)`, the workspace listing index, and a separate creator index.
- Added shared Zod schemas and inferred types for project responses, create and update inputs, UUID parameters, list queries, and paginated responses. Strict write contracts accept only `name` and `description`; PATCH requires at least one editable field.
- Added a reusable `ZodValidationPipe` that returns parsed values and reports `400 VALIDATION_ERROR` with issue codes, paths, and messages. Name trimming, numeric query limits, and defaults reach the controller through the parsed output.
- Registered `ProjectsModule` and added create, list, detail, PATCH, and DELETE routes under `/api/projects`. Applied `@RequireWorkspace()` and `@CurrentWorkspace()` to use the authenticated session and current membership.
- Implemented server-derived organization and creator IDs, organization-scoped queries, and uniform `404 PROJECT_NOT_FOUND` responses. Updates preserve attribution and creation time, keep omitted fields unchanged, allow `description: null`, and set `updated_at` using the database clock. Responses serialize dates as ISO strings.
- Added newest-first keyset pagination using `(created_at, id)`, a default page size of 25, a maximum of 100, and `limit + 1` lookahead. The next cursor comes from the last returned row only when another page exists.
- Added versioned, workspace-bound base64url cursors with strict payload, length, encoding, UTF-8, timestamp, and UUID validation. Invalid or different-workspace cursors return `400 INVALID_PROJECT_CURSOR`.
- Made the MVP project policy explicit: owners, admins, and members can perform all project CRUD actions. Other role values receive `403 PROJECT_PERMISSION_DENIED` before database access.
- Extended credentialed CORS to allow PATCH and DELETE. Added preflight assertions for the allowed origin, credentials, methods, and content-type header.
- Added unit and HTTP integration coverage for validation, permissions, ownership preservation, membership revocation, workspace switching, cross-workspace access, and pagination with tied timestamps and a deleted cursor boundary.
- Added four direct database integrity tests for nonexistent organization and creator references, organization cascades, and restricted creator deletion. Tests verify that unrelated workspace data and global users survive organization deletion.

## Decisions & why

- **Decision:** Keep ownership and creator attribution under server control.
  - **Why:** Client input must not select another tenant or rewrite historical attribution. Creator references point to the global user so they survive membership removal.
- **Decision:** Use keyset pagination with millisecond timestamps and an ID tie-breaker.
  - **Why:** Keep page boundaries deterministic and preserve timestamp precision when values pass through JavaScript dates and cursor serialization.
- **Decision:** Check project permissions at each service entry point.
  - **Why:** The workspace guard establishes current membership, while the service applies the action policy before accessing project data. Every query still includes its organization boundary.
- **Decision:** Test migration rules directly through Drizzle with bare user and organization fixtures.
  - **Why:** HTTP validation alone cannot prove foreign-key behavior. Minimal fixtures isolate project constraints from unrelated authentication and invitation references.

## Problems & fixes

- **Problem:** The listing query used bare `DESC`, while its index used `DESC NULLS LAST`.
  - **Fix:** Made both sort expressions explicitly use `DESC NULLS LAST`. On a disposable PostgreSQL 18 database with 20,000 projects, the original query scanned and sorted all rows; the matching order used the listing index and read the 26 rows needed for one page plus lookahead.
- **Problem:** Browser preflight responses did not allow the update and delete methods.
  - **Fix:** Added PATCH and DELETE to CORS and checked the allowed-methods header in tests. An OPTIONS response with status `204` alone does not establish that the requested method is permitted.
- **Problem:** The creator-deletion test initially expected the same SQLSTATE as an invalid foreign-key insert.
  - **Fix:** Asserted PostgreSQL 18's observed `23001` (`restrict_violation`) for the restricted deletion and `23503` (`foreign_key_violation`) for missing references, together with the exact constraint names. Retention assertions confirm failed statements leave the existing rows intact.

## Learned

- Matching index columns and sort direction is not enough: null ordering can determine whether PostgreSQL uses the index to satisfy `ORDER BY` and `LIMIT`.
- A cursor represents a seek boundary, so pagination can continue even after the boundary row is deleted. The cursor does not provide a snapshot or grant workspace access.
- Membership checks, action permissions, tenant-scoped queries, and database constraints enforce different parts of the ownership model.
- Database tests should identify the constraint that rejected an operation and verify the surviving data, rather than accepting any database error as success.
